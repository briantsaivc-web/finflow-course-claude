# 開發模式的典範轉移

<div class="lead">為什麼自己指揮 AI 做，比外包等別人做更值得？先不談錢——光這三件事就分出高下。</div>

| 比較維度 | 外包或等待工程團隊 | 你親自指揮 AI 一改再改 |
| :--- | :--- | :--- |
| **溝通成本** | 需求文件來回往返數週 | 自然語言即時對話修正 |
| **細節掌控** | 工程師常以技術限制回絕 | 核心商業邏輯由你親自拍板 |
| **改版速度** | 改一版耗時以月為單位 | 5 天推進 49 次版本，至今 74 次 |

- 本書說的「<b>疊代</b>」就是這件事：做一點、看一眼、再改一點，重複很多次
- **結論**：工具門檻消失後，領域專家的商業直覺才是最貴的資產

# 借鏡經典：拆解再重構

<div class="lead">借鏡不是抄襲，是拆解經典骨架並更換靈魂。</div>

| 經典機制來源 | 傳統桌遊作法 | FinFlow 的在地改造 |
| :--- | :--- | :--- |
| **大富翁／現金流** | 骰子回合制、固定買地收租 | 引入真實職場工時與生活意外事件 |
| **記帳訓練** | 紙筆手寫記帳，節奏拖沓冗長 | 一開始電腦幫你記，你熟了才自己記 |
| **勝負判斷** | 單純比拚現金或累積資產 | 結合幸福感、品格帳本與健康指標 |

- **怎麼拆**，三個問題就夠：① 它的**一個回合**在做什麼？② 哪一段**最拖時間**？③ 哪一段**跟台灣現實對不上**？
- 第 ① 題的答案留著，第 ②③ 題的答案就是你要動刀的地方

# 守住邊界：先砍成 MVP

<div class="lead">你腦中的完整版，永遠比第一版能做出來的大十倍。</div>

<div class="grid">
  <div class="box">
    <strong>宏大願景</strong><br>
    全功能多人線上金融帝國
  </div>
  <div class="arrow">➔</div>
  <div class="box red">
    <strong>無情揮刀</strong><br>
    砍掉商城・砍掉拍賣・砍掉連線
  </div>
  <div class="arrow">➔</div>
  <div class="box blue">
    <strong>最小可行產品 (MVP)</strong><br>
    單機可跑・數值精準・規則可驗
  </div>
</div>

- **一句話判準**：<span class="highlight">沒有它，這東西就跑不完一輪嗎？</span>不會，就砍
- **定義**：MVP 是「最小**能用**」，絕不是「最小**能想**」——做遊戲就是最小能玩，做工具就是最小能跑完一次
- 動刀之前先看第 29 頁：**先做機制，還是先做內容**

# 實戰案例：FinFlow 最初的 MVP

<div class="lead">一開始很小，小到一個週末就能把規則從頭驗到尾。</div>

| 卡牌與模組類別 | MVP 最初規劃規模 | 設計初衷與目標 |
| :--- | :--- | :--- |
| **職業卡** | 6 張（含月薪與月支出） | 建立基礎現金流級距差距 |
| **機會卡** | 小額 14 張、大額 10 張 | 驗證主動收入與槓桿邏輯 |
| **事件卡** | 生活誘惑 16 張、市場 12 張 | 考驗財務情商與突發應變 |
| **對手邏輯** | 3 種基礎電腦對手 | 拿來比較遊戲是不是太難或太簡單 |

- 合計 **58 張**——聽起來不少，但每張只有「名稱＋兩三個數字」，一個下午用 AI 就產得完
- 規模小才能極速除錯，地基穩了才准擴充

# 定下不能被打破的原則

<div class="lead">鐵律是人類給 AI 的韁繩，不准因施工難度而妥協。</div>

<div class="grid">
  <div class="box red">
    <strong>失控的風險</strong><br>
    AI 遇到技術障礙時<br>
    <i>會擅自簡化甚至修改遊戲規則</i>
  </div>
  <div class="arrow">➔</div>
  <div class="box">
    <strong>造物者的韁繩</strong><br>
    動手前立下不能改的原則<br>
    <i>技術可以換，原則不能動</i>
  </div>
  <div class="arrow">➔</div>
  <div class="box blue">
    <strong>審核底線</strong><br>
    不需懂代碼語法<br>
    <i>看懂原則是否被違背即可</i>
  </div>
</div>

- **不懂程式怎麼審？把舉證責任丟回去**：每次交付都要求 AI 先回答「這次有沒有違反我的三條原則？違反在哪？」
- 沒有鐵律的協作，產品最終會淪為 AI 便宜行事的拼裝車

# FinFlow 的三條鐵律

<div class="lead">先講要避免的事，術語擺後面——你不用會，但你要認得出被違反。</div>

- **鐵律一：改畫面，不准動到算錢的地方**
  算規則、算金額的那一段叫**引擎**，你看得到的版面叫 **UI**；調版面就只准動版面
- **鐵律二：卡片的數字放在單獨的清單裡，不准寫進程式**
  這樣加卡、改金額都不必動程式（術語叫**資料驅動**）
- **鐵律三：每一塊錢的進出都要留下一筆紀錄**
  就是**流水帳**（會計上叫**分錄**）；收支加總對不上，代表有錢憑空出現或消失

<div class="grid">
  <div class="box">
    <strong>工程師的把關方式</strong><br>
    逐行檢查程式碼架構與語法
  </div>
  <div class="arrow">➔</div>
  <div class="box blue">
    <strong>你的把關方式</strong><br>
    拿「三條鐵律」作為退件標準
  </div>
  <div class="arrow">➔</div>
  <div class="box red">

  </div>

**你不用看程式，看這三個徵兆就夠：**

| 你觀察到 | 違反了 |
| :--- | :--- |
| 只是調了版面，**算出來的數字卻變了** | 鐵律一 |
| AI 說「要多加一張卡，得改程式」 | 鐵律二 |
| 收入減支出，**跟畫面上的餘額對不起來** | 鐵律三 |

# 難度分期的智慧

<div class="lead">先把地基打牢，進階複雜功能刻意延後。每一階都要有你看得出來的完成條件。</div>

| 階段 | 在做什麼 | 你怎麼知道做完了 |
| :--- | :--- | :--- |
| **第 1 階** | 單機規則跑通 | 從頭玩到尾**不會卡住、不會當掉** |
| **第 2 階** | 數值平衡 | 連玩三局，**不會每局都太簡單或太難** |
| **第 3 階** | 介面拋光 | 給沒玩過的人，**他不用問就知道按哪裡** |
| **第 4 階** | 多人連線 | 兩台裝置同時玩，**兩邊看到的畫面一致** |

- 太早引入多人連線，或太早架那台「幫大家同步資料的主機」，都是專案腰斬的元兇

# 點子難度分級工作表

<div class="lead">動手之前，先將你的構想無情歸類。</div>

| 分級類別 | 判定標準 | 具體功能處置策略 |
| :--- | :--- | :--- |
| **現在做 (MVP)** | 沒有它，這東西根本跑不完一輪 | 職業基本盤、固定輪數、買賣結算 |
| **之後做 (Next)** | 有它更豐富，但沒有也能用 | 技能樹深度、特殊事件、自動升級 |
| **也許不做 (Never)** | 開發成本極高，邊際效益未知 | 即時語音聊天、自定義換裝、複雜拍賣 |

- 隨時拿著這張表，砍掉 AI 試圖為你塞入的過度設計
